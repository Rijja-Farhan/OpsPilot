# Decisions log

## 2026-11-01: Rebrand domain from SaaS to fintech
Chose a fictional fintech (Northwind Pay) so public banking-support datasets (Banking77, Bitext, CFPB, NAB) map onto our ticket categories with minimal remapping. Trade-off: we still need to write the glue (customer/ticket links, incident clusters) and the policy KB ourselves.

## 2026-11-01: A1 uses LLM only where language is needed (docs/spec-a1.md)
Ticket-by-ID and by-customer lookups are plain code: exact, deterministic, free, and an LLM there only adds error. The LLM handles free-text ticket questions (given the looked-up ticket as context), policy questions (given retrieved docs, must cite) and the fallback intent call. Router is regex first, LLM intent only if no regex matches. A lookup is "pure" if the text left after removing the ID contains only lookup words ("show", "ticket", "details"); anything else with an ID is a free-text ticket question.

## 2026-11-01: One SDK, provider table in config (plan-a1 section 3)
Groq, OpenAI and Ollama expose OpenAI-compatible endpoints, so `llm.py` uses the `openai` SDK and `config.PROVIDERS` holds base URL, key env var and model. Switching provider is one `.env` line. JSON mode is requested but output is always Pydantic-validated, with one retry that feeds the validation error back, then a typed `LLMError` (never an exception). A `fake` provider runs through the same code path via a duck-typed client (`fake_llm.py`) so tests are offline. Model IDs in the table are unverified placeholders until checked against each provider's model list.

## 2026-11-01: Citations are built in code, not by the model
The model lists sources it used, but `policies.answer` keeps only sources that were actually retrieved and fills `effective_date` from the doc's front matter. A fabricated or superseded source (in default mode) is dropped; if none survive, no answer is given. Retrieval is BM25 over whole current docs (A4 replaces it with embeddings and chunking). History questions (keyword check) include superseded docs.

## 2026-11-01: Banking77 intent -> category mapping (tools/gen/make_tickets.py)
The 77 intents map to the 8 labels in `CATEGORY_INTENTS` (the generator asserts every intent is mapped). Judgement calls: unrecognised card/cash/direct-debit payments and compromised card or lost phone -> `fraud_security`; top-ups and pending/reverted payments -> `transfers_payments`; refund requests, double charges and wrong cash amounts -> `disputes_refunds`; country/currency/age/exchange-via-app questions -> `other`. Banking77 has no loan intents, so the A1 sample has zero `loans_credit` tickets (CFPB would supply those later). `T-9001` is a hand-written prompt-injection fixture appended to the 300 sampled tickets.

## 2026-11-01: A3 tools live behind our own MCP server over a mock HTTP API (docs/spec-a3.md)
Chain: agent -> MCP client (stdio) -> `mcp_server` -> HTTP -> `mockapi` (FastAPI) -> `data/*.jsonl`. The mock API is a separate process so the MCP server is a real wrapper over a network service, with real failure modes (404, 422, 503, timeouts), not a function import. The server holds no business logic. Used the official `mcp` SDK (v2.x: `MCPServer`, `Client`); it is a protocol library, not an agent framework, so the plain-SDK rule in `AGENTS.md` still stands. `llm.complete()` gained an optional `tools=` argument and returns `tool_calls`; it stays the only module that imports the LLM SDK.

## 2026-11-01: One error contract for every tool, gates in code not in the prompt
Every tool returns data or `{"error": {"code", "message", "retryable"}}` with codes `not_found`, `invalid_argument`, `upstream_unavailable` (retryable), `rate_limited` (retryable). Tools never raise and never return a stack trace or an upstream body; text fields are capped at 2,000 chars and lists at 50 rows, because large tool output is a context-rot source. Errors from inside the MCP SDK (its own schema validation) are mapped to the same contract by `ToolBox.call`. Two rules are enforced in `agent.py` rather than trusted to the prompt: `add_ticket_note` (the only write) is refused unless the user's own message mentions a note, and an identical repeated call is refused (`duplicate_call`) so the agent cannot loop on a `not_found`. Both are tested with scripted fake-provider turns, including a prompt injection in ticket T-9001 that tries to trigger a write.

## 2026-11-01: A1's free-text ticket path now goes through the agent
In A1, "why is T-1001 still open?" made one LLM call with the ticket pasted in. Now it, and any question about a customer ID that is not a bare lookup, goes to the tool-calling agent, which can also check customer history and policy. Bare lookups ("show T-1001", "tickets for C-17") keep the plain-code path with no LLM and no tools. The A1 single-shot helper was removed rather than kept as a second path; the two A1 tests that covered it were replaced by agent tests. Cost: a free-text ticket question now needs the mock API running.

## 2026-11-01: Tool design change after watching the agent misuse `search_tickets` (the A3 misuse note)
Observed on Groq (`openai/gpt-oss-120b`), question "is C-5 a premium customer, and do they have any open fraud tickets?": in 3 of 3 runs the model called `search_tickets` with `category: "fraud"`, which is not a category (`fraud_security` is). It recovered from the error message each time, but cost a round trip. Three fixes tried, each measured with the same question:
1. Description lists the valid values and maps "fraud" to `fraud_security`: no effect, still 3 of 3 wrong first guesses.
2. Put the values in the JSON schema as an enum: made it worse. Groq validates tool arguments against the schema itself and rejects a bad value with HTTP 400 before we see it, so the model could not self-correct and the request failed (`provider_error`). Reverted. Lesson: provider-side schema enforcement turns a recoverable tool error into a hard failure, so keep validation (and the helpful error) in our server.
3. Kept: the server accepts an unambiguous fragment (`fraud` matches only `fraud_security`) and says what it did with `"filters_normalized": {"category": "fraud_security"}`. Ambiguous or unknown values still return `invalid_argument` listing the allowed values. Result on the same question, 3 of 3 runs: 2 tool calls and 0 errors, down from 3 calls and 1 error. Trade-off: the server now interprets input a little, which is why the applied value is echoed back instead of applied silently.
